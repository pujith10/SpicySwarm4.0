Executive SummaryThis document presents the complete implementation plan for the Hybrid Agentic Architecture (HAA) — a novel multi-agent AI framework proposed in the research paper "Bridging Generative AI and Agentic Autonomy." The plan covers the project rationale, system architecture, technology stack, module-by-module implementation guide, gap-to-solution mapping, evaluation strategy, and deployment roadmap.The HAA addresses six critical technical gaps identified through a systematic review of sixteen seminal research papers. The core innovation is a Planner–Executor–Validator (PEV) triad that enforces independent verification, prevents self-validation bias, and sustains goal congruence across long-horizon multi-step tasks.AttributeDetailsProject TitleHybrid Agentic Architecture (HAA) Demo SystemResearch PaperBridging Generative AI and Agentic Autonomy (IEEE Format)InstitutionBennett University, Greater Noida, IndiaPrimary LanguagePython 3.11+ (Backend), JavaScript/React (Frontend)LLM BackboneAnthropic Claude (claude-sonnet-4 via API)Vector DatabaseFAISS (local) / Pinecone (cloud)Knowledge GraphNeo4j (Docker)FrameworkLangChain + LangGraph for agent orchestrationDeployment TargetDocker Compose (local) / AWS EC2 (cloud)2. Research Background & Problem Statement2.1 The Transition from Generative AI to Agentic AIGenerative AI systems built on Large Language Models (LLMs) are fundamentally reactive — they respond to a prompt and produce an output, but lack the ability to plan across time, use tools autonomously, or recover from errors. Agentic AI is the next paradigm: systems that can observe their environment, reason about goals, decompose tasks, execute tools, and revise plans in a continuous loop.The ReAct (Reason + Act) algorithm formalizes this loop:Thought → Action → Observation → UpdateThis loop prevents the "one-shot failure" common in standard LLMs, where a single generation step is expected to answer a complex multi-step problem. However, naive agentic loops introduce new classes of failures that the HAA is specifically designed to overcome.2.2 Identified Technical Gaps (from Literature Review)The following six gaps were identified by reviewing sixteen seminal works. Each gap directly motivates a specific architectural component of the HAA:#Gap / ChallengeCategoryReferencesHAA Solution1Self-Verification Bias — Executor validates its own output, reinforcing errorsArchitectural[8], [16]Independent Validator Agent (PEV Triad)2Contextual Drift — Original goal lost as context window saturates in long tasksArchitectural[6], [12]Hierarchical Memory Anchoring3Static Planning Fallacy — No revision when tools return unexpected resultsLogic Flow[3], [7]Dynamic Re-Decomposition Loop4Indirect Prompt Injection — Malicious instructions in retrieved data hijack executionSecurity[5], [10]Sandboxed Execution + Token Scrubbing5High Retrieval Latency — Sequential RAG + Graph queries cause slowdownInfrastructure[4], [13]Asynchronous Parallel Retrieval Orchestrator6Goal Misalignment in Meta-Entrepreneurial Agents — Autonomous financial agents drift from user objectivesEconomic[14]Consensus Auditing (Auditor Sentinel Module)3. System Architecture3.1 Architecture OverviewThe HAA implements a closed-loop feedback system comprising five core layers: Context Retrieval, Planner Agent, Executor Agent, Validator Agent, and Memory Module. The design principle is verification over generation — every output from the Executor is audited by an independent Validator before being returned to the user.3.2 Core Component Descriptions3.2.1 Context Retrieval Layer (RAG + Knowledge Graph)The retrieval layer solves the High Latency gap by running two retrieval threads asynchronously. The Vector Database (FAISS/Pinecone) performs semantic similarity search over embedded document chunks. The Knowledge Graph (Neo4j) traverses entity-relationship triplets for multi-hop reasoning. A Ranked Fusion Layer merges both streams into a single context window using Reciprocal Rank Fusion (RRF) scoring.Input: User query stringOutput: Retrieved chunks + KG triplets + relevance scoresTechnology: FAISS, Neo4j, LangChain RetrieverGap Addressed: High latency in hybrid RAG + Graph retrieval3.2.2 Planner AgentThe Planner Agent receives the user goal and retrieved context, then decomposes the goal into a structured sub-task list. Each sub-task is assigned a tool type (rag, api, synthesis), a priority level, and a dependency chain. Critically, the original user goal is pinned as a global constant — the "Goal Anchor" — which is included in every subsequent agent call to prevent contextual drift.Input: User query + retrieved contextOutput: Structured plan (plan_id, subtasks[], goal_anchor)Technology: Claude claude-sonnet-4, LangGraph StateGraphGap Addressed: Static planning fallacy, contextual drift3.2.3 Executor AgentThe Executor Agent carries out each sub-task from the plan by calling the appropriate tool — either RAG retrieval for additional context, an external API, or an LLM synthesis call. It interacts with all tools through a Security Proxy Layer rather than directly, ensuring every action is validated against an Action Whitelist. The Executor also computes a State Delta log: an explicit record of uncertainties or unverified claims in its output.Input: Plan from Planner + contextOutput: Synthesized answer + state_delta (uncertainty log)Technology: Claude claude-sonnet-4, Tool-use API, Token Scrubbing MiddlewareGap Addressed: Self-verification bias, indirect prompt injection3.2.4 Validator AgentThe Validator is the architectural innovation that separates HAA from conventional agentic systems. It operates as a completely independent module — it does not share state with the Executor and receives only the original query, the retrieved context, and the Executor's output. The Validator checks three dimensions: hallucination risk (does the answer contradict retrieved context?), goal congruence (does the answer address the original goal?), and state delta resolution (were the Executor's noted uncertainties resolved?). If validation fails, a Refinement Signal is sent back to the Planner, triggering a recursive re-decomposition.Input: Original query + context + Executor output + state_deltaOutput: Verdict (PASS/REFINE) + refined answer + gaps foundTechnology: Claude claude-sonnet-4 with constrained system promptGap Addressed: Self-verification bias (primary), contextual drift3.2.5 Memory ModuleThe Memory Module maintains two types of state. Short-term memory tracks the current task's sub-goal completion status and is updated after each Executor cycle. Long-term memory stores validated outputs, user preferences, and entity relationships across sessions. This dual-memory approach implements Hierarchical Memory Anchoring from Section IV-C of the paper.Short-term: In-memory Python dict (LangGraph state), cleared per sessionLong-term: Redis (fast KV store) + SQLite (structured history)Gap Addressed: Contextual drift in long-horizon planning3.2.6 Security Proxy LayerEvery tool call from the Executor passes through the Security Proxy before execution. The proxy validates the requested action against an Action Whitelist derived from the Planner's approved sub-tasks. A Token Scrubbing Middleware NLP filter scans all retrieved data for imperative language patterns and neutralizes them before they reach the Executor's context window.Action Whitelist: JSON config loaded at pipeline startToken Scrubbing: spaCy dependency parser for imperative verb detectionGap Addressed: Indirect prompt injection via tool use4. This ensures the Goal Anchor (original user query) is never mutated or dropped across the pipeline:# pipeline/state.pyfrom typing import TypedDict, List, Optionalclass PipelineState(TypedDict):    query: str                    # Immutable Goal Anchor    retrieved_chunks: List[str]   # RAG output    kg_triplets: List[str]        # Knowledge Graph output    plan: dict                    # Planner output    execution: dict               # Executor output    state_delta: str              # Executor uncertainty log    validation: dict              # Validator output    final_answer: str             # Validated final output    retry_count: int              # Re-planning counter (max 2)5.3 Module 1 — Context Retrieval LayerThe retrieval layer uses Python's asyncio to fire both the FAISS vector search and the Neo4j KG traversal simultaneously. The results are fused using Reciprocal Rank Fusion before being returned to the Planner.# agents/rag_retriever.py (simplified)import asynciofrom langchain_community.vectorstores import FAISSfrom neo4j import AsyncGraphDatabaseasync def retrieve_context(query: str) -> dict:    # Fire both retrievals concurrently    chunks, triplets = await asyncio.gather(        semantic_search(query),    # FAISS        kg_traversal(query)        # Neo4j    )    fused = reciprocal_rank_fusion(chunks, triplets)    return { 'chunks': fused, 'triplets': triplets }5.4 Module 2 — Planner AgentThe Planner receives the query + context and calls Claude with a tightly scoped system prompt that forces structured JSON output. The Goal Anchor is explicitly set here and never modified by downstream agents.# agents/planner.py (simplified)PLANNER_SYSTEM = '''You are the Planner Agent in a HAA pipeline.Decompose the user goal into 3-5 sub-tasks.Output ONLY valid JSON: {plan_id, goal_anchor, subtasks[]}Each subtask: {id, task, tool, priority, depends_on}'''async def plan(state: PipelineState) -> PipelineState:    response = await claude_call(PLANNER_SYSTEM, state)    state['plan'] = parse_json(response)    return state5.5 Module 3 — Executor AgentThe Executor iterates over each sub-task in the plan, calls the appropriate tool through the Security Proxy, and synthesizes results. It explicitly generates a State Delta — a required field listing any unresolved uncertainties — which it passes to the Validator for independent review.# agents/executor.py (simplified)EXECUTOR_SYSTEM = '''You are the Executor Agent.Execute each sub-task using only approved tools.You MUST include a 'state_delta' field listing any uncertainty.Output ONLY valid JSON: {answer, state_delta, confidence}'''async def execute(state: PipelineState) -> PipelineState:    proxied_tools = security_proxy.wrap(TOOL_REGISTRY)    response = await claude_call(EXECUTOR_SYSTEM, state,                                 tools=proxied_tools)    state['execution'] = parse_json(response)    state['state_delta'] = state['execution']['state_delta']    return state5.6 Module 4 — Validator Agent (Core Innovation)The Validator is the most critical module. It receives the original query and context (not the Executor's working state) and audits the answer along three axes. If it issues a REFINE verdict, the LangGraph node routes back to the Planner. A retry_count guard prevents infinite loops.# agents/validator.py (simplified)VALIDATOR_SYSTEM = '''You are an independent Validator Agent.You NEVER see the Executor's internal reasoning — only its output.Check: (1) hallucination vs context, (2) goal congruence,       (3) state_delta resolution.Output ONLY JSON: {verdict, hallucination_risk, goal_congruent,                   gaps_found[], refined_answer}'''async def validate(state: PipelineState) -> PipelineState:    # Validator only sees query, context, and executor output    audit_input = {        'query': state['query'],          # Goal Anchor        'context': state['retrieved_chunks'],        'answer': state['execution']['answer'],        'state_delta': state['state_delta']    }    response = await claude_call(VALIDATOR_SYSTEM, audit_input)    state['validation'] = parse_json(response)    return state5.7 Module 5 — LangGraph Pipeline DefinitionLangGraph's StateGraph connects all agents as nodes with conditional edges. The key conditional edge from the Validator implements the Dynamic Re-Decomposition Loop: a REFINE verdict routes back to the Planner, while a PASS verdict routes to the output.# pipeline/graph.pyfrom langgraph.graph import StateGraph, ENDdef should_refine(state: PipelineState) -> str:    verdict = state['validation'].get('verdict', 'PASS')    if verdict == 'REFINE' and state['retry_count'] < 2:        state['retry_count'] += 1        return 'planner'   # Route back to re-plan    return 'output'        # Accept and finalizedef build_pipeline() -> StateGraph:    g = StateGraph(PipelineState)    g.add_node('retriever', retrieve_context)    g.add_node('planner',   plan)    g.add_node('executor',  execute)    g.add_node('validator', validate)    g.set_entry_point('retriever')    g.add_edge('retriever', 'planner')    g.add_edge('planner',   'executor')    g.add_edge('executor',  'validator')    g.add_conditional_edges('validator', should_refine)    return g.compile()5.8 Module 6 — Security Proxy & Token ScrubbingThe security proxy wraps every tool in an access-control layer. The token scrubber uses spaCy to detect and neutralize imperative instruction-like patterns in retrieved text before they reach the Executor's context window — preventing indirect prompt injection.# agents/security_proxy.py (simplified)import spacynlp = spacy.load('en_core_web_sm')def scrub_tokens(text: str) -> str:    doc = nlp(text)    neutralized = []    for sent in doc.sents:        root = sent.root        # Detect imperative: VB with no subject and second-person context        if root.pos_ == 'VERB' and root.dep_ == 'ROOT':            has_subj = any(t.dep_ in ('nsubj','nsubjpass') for t in root.children)            if not has_subj:                # Convert to passive/informational form                neutralized.append(f'[Note: {sent.text}]')                continue        neutralized.append(sent.text)    return ' '.join(neutralized)6. Limitations & Future Work10.1 Current LimitationsLatency: Full pipeline with two LLM calls (Executor + Validator) adds ~3-4 seconds vs. a single LLM call. Mitigation: streaming output to the frontend hides perceived latency.Cost: Three Claude API calls per query (Planner, Executor, Validator) increases token cost. Mitigation: use claude-haiku for Planner on simple queries, reserve sonnet for Executor and Validator.Knowledge Graph Coverage: The KG must be manually populated from the source corpus. Automated KG construction from PDFs is a known hard problem.Simulated Tools: In the current demo, the Executor's "tools" are simulated as LLM synthesis calls. A production system would integrate real external APIs.10.2 Future ExtensionsMulti-Agent Parallelism: Run multiple Executor agents in parallel for independent sub-tasks, then merge results before Validation (fan-out/fan-in pattern).Streaming Validator: Validate the Executor's output token-by-token rather than waiting for completion, enabling earlier error detection.Meta-Entrepreneurship Module: Implement the Consensus Auditing (Auditor Sentinel) module for financial/trade agent alignment as described in Section IV-G of the paper.Automated KG Construction: Use Claude to extract entity-relation triplets from ingested documents automatically during the ingest pipeline.Fine-tuned Validator: Train a smaller, faster model specifically on validation tasks to reduce latency and cost of the validation step.Multi-modal Support: Extend the Executor to process images and structured data (CSV, JSON) in addition to text, enabling scientific and industrial use cases from Section II-D.11.
